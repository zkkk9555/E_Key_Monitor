# spec: refresh-project-conventions

Status: ready-for-agent
Triage: 标签 `ready-for-agent`（本地 markdown tracker，见 `docs/agents/issue-tracker.md`）

## Problem

项目是用户自己开发并长期维护的 Windows 悬浮提示工具 `E_Key_Monitor`。仓库克隆到本机后，`AGENTS.md`、`README.md`、中文说明书三份文档里保留着**开发当时的快照**：旧提交号、旧 SDK 版本、旧便携包输出路径、旧的环境假设（E 盘与游戏安装），以及**已经和代码不一致的行为描述**（独立模式被写成“必须选游戏目录”）。

后果是具体的：

- 下一个 AI 维护者读到 `AGENTS.md:317` 会以为独立模式必须先选游戏目录，于是把 `MainForm.cs:535` 的“可跳过”分支当成 bug 修掉——文档会把代码改回去。
- 文档里钉着 `838e43e Initial commit`，任何人拿它当基线都会在错误的前提上工作。
- `docs/agents/domain.md:9` 指向 `docs/adr/`，该目录不存在；将来做决策时没有落点。
- 三份文档各写一遍“当前核查状态”，三处都会同时过期。
- 没有任何机制在改动发生后发现“文档已经和代码不一样了”——这次的过时就是这么积累出来的。

用户诉求：理解项目、整理项目规范、把过时的地方修好并补全。

## Solution

把“项目规范”收敛成**一套可自检的约定**：

1. **`AGENTS.md` 校准**：逐条对照当前代码与仓库状态修正事实，补齐遗漏的既有行为（单文件发布、8s 关闭看门狗、1s 渲染自愈、独立模式可跳过、10 分钟启动超时、config 写回带 BOM、观察键可配置），文件职责树与真实仓库对齐。
2. **消除重复事实源**：核查状态只保留在 `AGENTS.md` 一处，`README.md` 与说明书改为指向它。
3. **补全缺失的落点**：建 `docs/adr/`，把三条已定、难回退、且有真实取舍的决策写成 ADR；`docs/agents/domain.md` 的指针落到真实文件。
4. **旧名迁移**：`autopilot` → `automatt`（skill 已改名），并把启用凭据写成机器可判的一行。
5. **加一道会红的门**：`tools/verify-conventions.ps1` 把上面这些约定变成可执行检查——文件树与真实仓库一致、8 BAT 纯 ASCII、所有 PS1 带 BOM、`config.json` 字段齐、文档里不出现会腐烂的提交号、仓内不出现旧 skill 名、安全边界静态零命中。

## User Stories

1. 作为下一位 AI 维护者，我希望读到 `AGENTS.md` 就能知道程序当前**真实**怎么跑，以便我不把正确的行为改坏。
2. 作为下一位 AI 维护者，我希望 `AGENTS.md` 里的文件树和仓库真实内容一致，以便我能相信这份文档。
3. 作为下一位 AI 维护者，我希望文档不钉死会变的东西（提交号、SDK 小版本、临时输出目录），以便它不会再次腐烂。
4. 作为用户，我希望 README 和中文说明书与 `AGENTS.md` 不冲突，以便我按说明书操作不会踩坑。
5. 作为用户，我希望说明书告诉我“独立模式可以跳过游戏目录”，以便我只想看圆点时不被多余流程卡住。
6. 作为维护者，我希望有一条命令能告诉我“文档/约定现在是否还成立”，以便我在提交前自查，而不是等下一个维护者发现。
7. 作为维护者，我希望这条命令是**红的**（能真的抓到问题），以便我不把它当成安慰剂。
8. 作为未来做决策的人，我希望有一个 `docs/adr/` 落点，以便“当初为什么这么做”不会被下一次改动悄悄抹掉。
9. 作为用户，我不希望这轮整理改动任何运行时行为，以便我不用重新学习工具怎么用。

## Implementation Decisions

- **规范的文件分工保持不变**：`AGENTS.md` 仍是 AI 事实源，`README.md` 面向用户，中文说明书面向便携包使用者，`docs/agents/` 是 agent 侧约定。不新建同义文件。
- **核查状态单点化**：只保留 `AGENTS.md` 一处，带日期和“以实测命令为准”的复算方式；README 与说明书改为一行指针。
- **不钉提交号**：规范改为“以 `git log -1` 为准”，并让校验器禁止文档里出现 7/40 位十六进制提交号——这是本次腐烂的直接成因。
- **环境描述分层**：区分“仓库事实”（可在仓库内查证）与“部署机事实”（E 盘游戏路径等）。部署机路径标注为部署机路径，不再宣称是本机环境。
- **ADR 只写三条**：观察边界（只观察不干预）、单文件 self-contained 便携发布、配置随 EXE。判据 = 难回退 + 无上下文会让人困惑 + 有真实取舍（`domain-modeling/ADR-FORMAT.md:30-36`）。其余不写。
- **校验器放 `tools/` 不放根目录**：根目录 8 BAT / 5 PS1 的既有约定不被打扰；校验器自身是 PS1，同样带 BOM。
- **校验器不联网、不安装、不写仓库外文件**：只读仓库 + 只写标准输出。
- **旧名改写限于工作区内**：`AGENTS.md:370` 的 `autopilot` → `automatt`；工作区外（如 `~/.dsh/` 安装副本）不写。

## Testing Decisions

- **seam**：`tools/verify-conventions.ps1`（一个脚本、一个退出码）。红 = 非 0 退出 + 逐条 `FAIL` 行；绿 = 0 退出 + 逐条 `PASS` 行。
- **红基线**：先在**未修改**的文档上跑，必须红且能指名具体漂移（旧提交号、旧 skill 名、树缺 `docs/agents/`、指针落空）。
- **只测外部可观察行为**：校验器只看仓库里的文件和命令输出，不看实现细节。
- **代码门**（本轮不改 C#，仍跑）：`dotnet build -c Release` 退出码 0 / 0 警告；`dotnet format E_Key_Monitor.csproj --verify-no-changes` 退出码 0。
- **脚本门**：8 BAT 非 ASCII 字节数 = 0；全部 PS1 前 3 字节 = EF BB BF；PowerShell 5.1 静态解析无错误。
- **不测的**：不模拟 E 键、不启动游戏、不验证圆点颜色、不验证托盘菜单与快捷方式生成——本轮不碰运行时，这些一律不声称通过。

## Slices

- [x] **S1 约定校验器**（`tools/verify-conventions.ps1`）：11 类检查；红基线 = 当前漂移（实测 6 passed / 5 failed / exit 1）；修完绿（实测 11 passed / 0 failed / exit 0）。
- [x] **S2 AI 事实源校准**（`AGENTS.md`、`docs/agents/domain.md`、`docs/adr/0001-0003.md`）：事实逐条对齐 + 树补全 + ADR 落点 + 旧名改写。
- [x] **S3 用户文档对齐**（`README.md`、`E键监控工具中文使用说明书.md`）：消除与 `AGENTS.md` 的矛盾，核查状态改为单点指针。

## Out of Scope

- 不改 C# 运行时行为（安全边界、Hook、绘制、跟随逻辑一律不碰）。
- 不改技术栈、不引入第三方 NuGet 包、不加测试框架或 CI。
- 不启动游戏、不模拟键盘、不创建桌面快捷方式。
- 不删改 `.scratch/` 下已有的历史 spec/issue 记录。
- 不把 `docs/superpowers/` 下的历史计划文档重写成新格式。**（实测后放宽：只允许加一行状态批注，不改原正文——理由见下方「范围调整」）**

## Glossary

- **观察**：只被动读取键盘事件与进程存在性，不产生、拦截或修改输入。
- **独立模式**：不带参数运行，只显示圆点，不跟随游戏进程。
- **联合启动模式**：`--launch-game`，验证目录后启动原始 `StartGame.exe` 并进入跟随状态。
- **约定校验器**：`tools/verify-conventions.ps1`，把项目约定变成可执行检查的门。
- **部署机事实**：只在用户自己那台装了游戏的机器上成立的路径等事实。

## Further Notes

### 设计树（自答；用户 AFK，按 self-answer 策略以仓库/代码为依据）

Round 1
- **Q1「项目规范」具体指哪些文件？** → 答：`AGENTS.md` + `docs/agents/` + `docs/adr/`（新建）+ README/说明书的一致性。依据：`AGENTS.md:53-77` 的文件职责树 + `docs/agents/domain.md:7-9`。
- **Q2 文档该描述本机还是部署机？** → 答：仓库事实写本仓可查证的；游戏路径写成“部署机路径”并标注。依据：本机 `Test-Path 'E:\'` = False，`E:\Youxi\...` 不存在，而 `AGENTS.md:4-8` 仍断言 E 盘存在。
- **Q3 要不要加一个会红的校验器？** → 答：要。依据：用户诉求里的“可能有些地方已经过时了”指向机制缺失；`verification-gates.md:97-100` 要求新门自带红基线。

Round 2
- **Q4「当前核查状态」放哪？** → 答：只放 `AGENTS.md`，README/说明书改指针。依据：`writing-for-agents`「每条含义只有一个 source of truth」；现状是三份文档各写一遍。
- **Q5 规范要不要拆成多个文件？** → 答：不拆。依据：`writing-for-agents` 的 sprawl 风险是“push too much down”的另一面；本仓 1 个主文件 + 3 个 agent 约定文件刚好，`AGENTS.md` 才 380 行、未到需要拆的程度；拆分会增加指针，而当前指针已够用。

Round 3
- **Q6 ADR 写哪几条？** → 答：三条（观察边界 / 单文件发布 / 配置随 EXE）。依据：`ADR-FORMAT.md:30-36` 三条判据；其余（如菜单布局、颜色取值）可逆或不令人困惑，不写。
- **Q7 旧 skill 名与凭据行怎么处理？** → 答：仓内 `autopilot` 改成 `automatt`，并加机器可判的 `automatt: on` 独占一行。依据：改名迁移规则；仓内仅 `AGENTS.md:370` 一处命中。

Round 4（高赌注：这套规范会被长期依赖 → 真实场景五问）
- **Q8 谁在什么场景用，数据脏不脏？** → 答：下一位 AI 在克隆后的机器上读 `AGENTS.md` 改代码；脏数据 = 文档里的旧快照（本轮已列 10 条漂移）与用户自己机器上的 E 盘路径。
- **Q9 并发/重复/离线怎么办？** → 答：校验器只读仓库、无网络、可重复执行；改文档的人与跑校验器的人不冲突（只读）。“重复” = 同一事实被写在多处 → 本轮把核查状态收成单点，校验器用“文档里不得出现提交号”防止再次复制易腐事实。
- **Q10 失败长什么样、怎么发现？** → 答：校验器非 0 退出并逐条打印 `FAIL <检查名> <证据>`；文档漂移表现为 `FAIL doc-tree` / `FAIL stale-sha` / `FAIL old-skill-name`。
- **Q11 怎么回滚、谁来撤？** → 答：本轮是纯文档 + 一个新脚本，全部在 git 里，`git revert` 即可；未提交前可 `git checkout --`。不涉及不可逆动作。
- **Q12 以后怎么扩展、会不会挡住下一个人？** → 答：校验器按“检查名 + 证据”输出，新增约定 = 加一条检查；每条检查都指向 `AGENTS.md` 里的一条明文约定，不引入隐式规则，因此下一个人能看懂门在门什么、也能改门。

### 范围调整（实测后）

独立子代理的文档审计（`.scratch/refresh-project-conventions/audit-docs.md`）在实现阶段补出 4 条原 spec 没覆盖的漂移，同源、且都属于「过时的事实」，因此就地修掉并记在这里：

1. **两套桌面快捷方式同名不同目标**——EXE 托盘菜单建 `E键监控工具.lnk` + `启动StartGame和监控.lnk`（都指向 EXE）；`Create_Naraka_Monitor_Shortcut.ps1` 建 `E键监控工具.lnk` + `永劫无间（E键提示）.lnk`（都指向中文 BAT）。原文档只写了第一套。→ 已在 `AGENTS.md`「桌面快捷方式」一节分 A/B 两套写清。
2. **启动脚本会回退到多文件形态**（`bin\Release\net8.0-windows\win-x64\E_Key_Monitor.exe`），不是便携包形态。→ 已写进「构建和发布」。
3. **`.gitignore` 还排除 `.agents/` 和 `.codex/`**。→ 已补进「先读这里」的生成内容清单。
4. **已完成但复选框全空的计划文件**（`docs/superpowers/` 下 single-exe 的 plan 与 design）。→ 按「历史只追加、不重写」的原则，只加一行状态批注，指向 `AGENTS.md` 与 ADR-0002。
